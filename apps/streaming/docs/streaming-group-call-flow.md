## 概述

群组通话支持**3人及以上**的多人音视频通话，采用 **SFU (Selective Forwarding Unit)** 架构。

### 核心特点

- **媒体转发**: 通过SFU服务器转发，而非P2P直连
- **可扩展性**: 支持更多参与者（最多50人）
- **带宽优化**: 每个用户只上传一次流，SFU负责转发
- **统一管理**: 主持人可管理所有参与者

### 技术架构

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  用户A   │    │  用户B   │    │  用户C   │    │  用户D   │
│  (主持)  │    │  (参与)  │    │  (参与)  │    │  (参与)  │
└────┬─────┘    └────┬─────┘    └────┬─────┘    └────┬─────┘
     │               │               │               │
     │ ↑upload       │ ↑upload       │ ↑upload       │ ↑upload
     │ ↓download     │ ↓download     │ ↓download     │ ↓download
     │               │               │               │
     └───────────────┴───────────────┴───────────────┘
                     │
            ┌────────▼─────────┐
            │   SFU 服务器     │
            │  媒体流转发       │
            └──────────────────┘
```

## 阶段详解

### 阶段1: 发起群组通话

#### 消息 ①: group_invite (A → 服务器)

**发起方**: 主持人（用户A）  
**目的**: 邀请多个用户加入群组通话

**消息格式**:
```json
{
    "type": "group_invite",
    "user_id": "userA",
    "data": {
        "participants": ["userB", "userC", "userD"]
    },
    "timestamp": "2025-10-13T10:00:00Z"
}
```

**核心字段**:
- `participants`: 要邀请的用户ID数组

**服务器处理**:
- 调用 `CreateGroupCall(callerID, participants)`
- 检查所有用户是否在通话中
- 生成 call_id 和 room_id
- 创建Call对象，类型为 `group`
- 状态设置为 `inviting`

---

#### 消息 ②③④: group_invite (服务器 → B, C, D)

**发起方**: 服务器（批量转发）  
**目的**: 将邀请发送给所有被邀请者

**消息格式**:
```json
{
    "type": "group_invite",
    "user_id": "userA",
    "data": {
        "id": "call_1697184000",
        "type": "group",
        "status": "inviting",
        "caller_id": "userA",
        "participants": ["userA", "userB", "userC", "userD"],
        "room_id": "room_1697184000",
        "created_at": "2025-10-13T10:00:00Z"
    },
    "timestamp": "2025-10-13T10:00:00Z"
}
```

**核心字段**:
- `type`: `group` (群组通话)
- `participants`: 所有参与者列表（包含主持人）

---

### 阶段2: 参与者响应

#### 消息 ⑤⑥⑦: group_join (B, C, D → 服务器)

**发起方**: 各个被邀请者  
**目的**: 接受群组通话邀请

**消息格式**:
```json
{
    "type": "group_join",
    "user_id": "userB",
    "data": {
        "call_id": "call_1697184000"
    },
    "timestamp": "2025-10-13T10:00:05Z"
}
```

**服务器处理**:
- 调用 `AcceptCall(callID, userID)`
- 验证用户是否在参与者列表中
- 第一个接受时，更新通话状态为 `connected`
- 记录开始时间

---

#### 消息 ⑧: group_join (服务器 → 所有人)

**发起方**: 服务器（广播）  
**目的**: 通知所有参与者，有新成员加入

**消息格式**:
```json
{
    "type": "group_join",
    "user_id": "userB",
    "data": {
        "id": "call_1697184000",
        "participants": ["userA", "userB"],
        "status": "connected"
    },
    "timestamp": "2025-10-13T10:00:05Z"
}
```

**说明**: 每次有人加入，都会广播给所有已加入的成员

---

### 阶段3: 加入房间

#### 消息 ⑨⑪⑭: join_room (所有人 → 服务器)

**发起方**: 每个参与者（包括主持人）  
**目的**: 加入通话房间，建立信令通道

**消息格式**:
```json
{
    "type": "join_room",
    "room_id": "room_1697184000",
    "user_id": "userA",
    "timestamp": "2025-10-13T10:00:06Z"
}
```

**服务器处理**:
1. 创建或获取房间
2. 创建User对象并添加到房间
3. 创建WebRTC PeerConnection
4. 保存连接映射
5. 将用户添加到SFU

---

#### 消息 ⑩⑫⑮: room_info (服务器 → 加入者)

**发起方**: 服务器（响应）  
**目的**: 返回房间当前状态

**消息格式**:
```json
{
    "type": "room_info",
    "room_id": "room_1697184000",
    "user_id": "userB",
    "data": {
        "room_id": "room_1697184000",
        "users": [
            {
                "user_id": "userA",
                "username": "User userA",
                "is_muted": false,
                "is_video_on": true,
                "role": "host"
            },
            {
                "user_id": "userB",
                "username": "User userB",
                "is_muted": false,
                "is_video_on": true,
                "role": "participant"
            }
        ]
    },
    "timestamp": "2025-10-13T10:00:07Z"
}
```

---

#### 消息 ⑬⑯: user_joined (服务器 → 房间内其他人)

**发起方**: 服务器（广播）  
**目的**: 通知房间内已有成员，有新成员加入

---

### 阶段4: WebRTC连接建立

#### 关键区别: 每个人与SFU建立连接

在群组通话中，**不是用户之间互相连接**，而是**每个用户都与SFU服务器建立独立的连接**。

**连接模式**:
```
用户A ←→ SFU ←→ 用户B
          ↕
        用户C
          ↕
        用户D
```

**Offer/Answer流程**:
- 每个用户创建Offer，发送给SFU
- SFU返回Answer
- 交换ICE候选
- 建立加密的媒体通道

---

### 阶段5: 媒体流转发

#### SFU转发机制

**上行流程**:
1. 每个用户上传自己的音视频流到SFU
2. SFU接收所有用户的流

**下行流程**:
1. SFU将每个用户的流转发给其他所有用户
2. 用户A收到: B、C、D的流
3. 用户B收到: A、C、D的流
4. 以此类推...

**带宽计算**:
- 上行: 每个用户上传 1 条流
- 下行: 每个用户下载 (N-1) 条流 (N为总人数)

**示例** (4人群组):
```
用户A: ↑1条流  ↓3条流
用户B: ↑1条流  ↓3条流
用户C: ↑1条流  ↓3条流
用户D: ↑1条流  ↓3条流
```

---

### 阶段6: 参与者离开

#### 消息: group_leave (任意参与者 → 服务器)

**发起方**: 任意参与者  
**目的**: 离开群组通话（不结束通话）

**消息格式**:
```json
{
    "type": "group_leave",
    "user_id": "userC",
    "data": {
        "call_id": "call_1697184000"
    },
    "timestamp": "2025-10-13T10:10:00Z"
}
```

**服务器处理**:
- 从参与者列表移除该用户
- 更新通话信息
- 广播给其他参与者
- 如果离开的是主持人，通话结束

---

### 阶段7: 结束群组通话

#### 消息: call_end (主持人 → 服务器)

**发起方**: 主持人  
**目的**: 结束整个群组通话

**消息格式**:
```json
{
    "type": "call_end",
    "user_id": "userA",
    "data": {
        "call_id": "call_1697184000"
    },
    "timestamp": "2025-10-13T10:15:00Z"
}
```

**服务器处理**:
1. 验证是否为主持人
2. 更新通话状态为 `ended`
3. 记录结束时间和时长
4. 通知所有参与者
5. 清理所有资源

## 核心数据结构

### Call 对象（群组模式）

```json
{
    "id": "call_1697184000",
    "type": "group",
    "status": "connected",
    "caller_id": "userA",
    "participants": ["userA", "userB", "userC", "userD"],
    "room_id": "room_1697184000",
    "created_at": "2025-10-13T10:00:00Z",
    "started_at": "2025-10-13T10:00:05Z",
    "ended_at": null,
    "duration": 0
}
```

**与一对一的区别**:
- `type`: `group` (而非 `one_to_one`)
- `participants`: 包含3人或以上
- `caller_id`: 主持人ID

---

### Room 对象（群组模式）

```json
{
    "room_id": "room_1697184000",
    "name": "Group Call Room",
    "users": [
        {
            "user_id": "userA",
            "role": "host",
            "is_muted": false,
            "is_video_on": true
        },
        {
            "user_id": "userB",
            "role": "participant",
            "is_muted": false,
            "is_video_on": true
        },
        {
            "user_id": "userC",
            "role": "participant",
            "is_muted": false,
            "is_video_on": true
        }
    ]
}
```

**用户角色**:
- `host`: 主持人（发起者）
- `participant`: 参与者

## 与一对一通话的区别

### 功能对比

| 特性 | 一对一通话 | 群组通话 |
|-----|-----------|---------|
| **参与人数** | 固定2人 | 3-50人 |
| **连接方式** | P2P直连 | SFU转发 |
| **邀请方式** | call_invite | group_invite |
| **响应方式** | call_accept/reject | group_join/leave |
| **主持人** | 无 | 有（发起者） |
| **角色管理** | 无 | host/participant |
| **结束方式** | 任意方结束 | 仅主持人可结束 |
| **带宽消耗** | 低 | 中等 |
| **延迟** | 最低 | 中等 |

---

### 架构对比

#### 一对一通话（P2P）

```
用户A ←────直接连接────→ 用户B
    低延迟，高质量
```

#### 群组通话（SFU）

```
用户A ←┐
用户B ←┼→ SFU服务器 ←→ 每个用户只连接SFU
用户C ←┤                 SFU负责转发
用户D ←┘
    中等延迟，支持扩展
```

## 关键要点

### 1. 邀请模式

- **批量邀请**: 一次邀请多个用户
- **异步响应**: 用户可以不同时间加入
- **通知机制**: 每次有人加入都通知所有人

### 2. SFU架构优势

- **带宽优化**: 每人只上传1条流，不是N-1条
- **可扩展**: 支持更多参与者
- **稳定性**: 中心化管理，易于控制

### 3. 角色管理

- **主持人权限**:
  - 结束整个通话
  - 移除参与者（可扩展）
  - 控制会议设置（可扩展）

- **参与者权限**:
  - 随时离开（不影响其他人）
  - 控制自己的音视频
  - 发送消息

### 4. 性能考虑

**带宽需求**:
- 上行: 约 1-2 Mbps (取决于视频质量)
- 下行: 约 (N-1) × 1-2 Mbps

**示例** (720p, 4人群组):
- 上行: 1.5 Mbps
- 下行: 4.5 Mbps (3条流)

### 5. 状态同步

- 每次有人加入/离开，更新所有人的参与者列表
- 实时同步音视频状态（静音、视频开关）
- 确保所有人看到一致的状态
